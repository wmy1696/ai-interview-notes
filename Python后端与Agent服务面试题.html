00 · 先把三件事串起来

FastAPI 收到请求→ASGI 创建协程任务→事件循环调度→await LLM / DB / Tool→等待期间处理其他请求

Agent 服务的大部分时间不是在计算，而是在等待：等大模型返回、等数据库、等向量检索、等外部工具。因此它通常是 I/O 密集型。asyncio 能让单个线程在大量等待任务之间切换；FastAPI 基于 ASGI，天然适合承载这种异步请求、流式输出和长连接。

GIL 限制的是标准 CPython 中多个线程同时执行 Python 字节码的能力，但等待网络 I/O 时线程通常不会一直占着 GIL。因此对于典型 Agent 编排服务，首要问题往往不是 GIL，而是阻塞调用、超时、并发上限、背压、状态和可观测性。

一句话总览：GIL 解释 CPU 线程为什么不能自然并行；事件循环解释单线程怎么高效管理大量 I/O；FastAPI 则把这种异步模型包装成适合 Agent 的 Web 服务框架。

01 · Python 的 GIL 是什么？

30 秒口语回答

GIL 全称是全局解释器锁。在常规 CPython 进程里，同一时刻通常只有一个线程能执行 Python 字节码，所以多线程不能让纯 Python 的 CPU 密集计算真正并行。但这不代表 Python 线程完全没用：网络、文件等 I/O 等待期间会释放执行机会，一些 C 扩展也会主动释放 GIL，因此多线程仍适合不少 I/O 场景。CPU 密集任务一般考虑多进程、原生扩展或独立计算服务。

怎么真正理解

可以把一个 CPython 进程想象成一个办公室：里面可以有很多线程，但执行 Python 字节码需要拿到唯一的“工牌”。一个线程执行一小段后，解释器可能把机会交给另一个线程。

  • 并发不等于并行：多个线程可以交替推进，叫并发；同一时刻在多个 CPU 核上同时执行，才叫并行。
  • I/O 密集仍可受益：线程等待网络、磁盘时，别的线程可以继续工作。
  • CPU 密集受限制：两个纯 Python 计算线程往往不能同时占用两个核心执行字节码，还会产生切换开销。
  • GIL 不等于线程安全：一个业务操作可能由多条字节码组成，线程仍可能交错；共享状态依然需要锁或其他同步手段。

面试中的任务选型

任务常见方案理由
调用 LLM、HTTP API、数据库asyncio 或线程池主要时间花在等待 I/O。
少量同步阻塞 SDKasyncio.to_thread()把阻塞调用移出事件循环，但仍要限制线程池并发。
纯 Python 大量计算多进程 / 任务队列绕开单进程 GIL，并利用多核。
NumPy、推理引擎等确认底层实现不少 C/C++/CUDA 代码在计算时会释放 GIL，不能一概而论。
版本补充怎么说：较新的 Python 提供了可选的 free-threaded 构建方向，但面试讨论 GIL 时应先明确“我说的是常规 CPython 运行时”。不要直接说“新版本已经没有 GIL”，因为运行方式、扩展兼容性和性能权衡仍需结合实际环境。
常见错误：“有 GIL，所以 Python 不能并发”“用了多线程就绝对没有竞态”“asyncio 可以绕过 GIL 加速 CPU 计算”——这三句话都不对。

02 · asyncio 的事件循环怎么理解？

30 秒口语回答

asyncio 的核心是事件循环加协程。事件循环在一个线程中维护很多 Task：某个协程运行到 await，说明它现在要等 I/O，就主动交出控制权；事件循环转去执行其他已经就绪的任务。等 socket、定时器或 Future 完成后，再把原任务放回就绪队列继续执行。它是协作式并发，优势是用较低的线程成本管理大量 I/O 等待，不是让 CPU 代码自动并行。

用餐厅类比

一个服务员同时照看很多桌。给 A 桌下单以后，不会站在厨房门口干等，而是去服务 B 桌；厨房通知菜好了，再回来处理 A 桌。服务员就是事件循环，桌子是 Task，等待厨房就是 await I/O。

运行协程 A→A 遇到 await→注册等待并让出→运行 B/C→A 的 I/O 就绪→恢复 A

几个核心对象

概念作用
Coroutineasync def 定义的可暂停执行过程；调用它得到协程对象，不代表已经执行完。
Task被事件循环调度的协程包装；多个 Task 可以并发推进。
Future代表一个未来才会完成的结果，Task 本身也是 Future 的一种高层形式。
Event loop维护就绪任务、定时器和 I/O 通知，选择下一个可运行工作。
await等待一个 awaitable，并在未完成时主动把控制权还给事件循环。

最关键的面试点：await 不一定让出控制权

只有被等待的对象尚未完成、确实需要等待时，协程才会暂停。如果你在 async def 中调用同步阻塞函数，事件循环仍会被卡住。

import asyncio
import time

async def bad():
    time.sleep(3)          # 阻塞事件循环，其他请求也会被拖住

async def better():
    await asyncio.sleep(3) # 当前 Task 暂停，事件循环可运行其他 Task

async def legacy_sdk():
    result = await asyncio.to_thread(blocking_call)
    return result

并发不等于无限并发

semaphore = asyncio.Semaphore(20)

async def call_llm(prompt: str):
    async with semaphore:
        return await llm_client.generate(prompt, timeout=30)

真实 Agent 服务还要处理：超时、取消、重试、速率限制、连接池、背压和部分失败。async 只是并发机制，不会自动解决这些工程问题。

常见错误：在 async def 里使用同步 HTTP 客户端、time.sleep()、CPU 密集循环，都会堵住事件循环；给函数加上 async 关键字并不会让内部代码自动异步。

03 · FastAPI 为什么适合 Agent 服务？

30 秒口语回答

Agent 服务通常是 I/O 密集型：一次请求会调用 LLM、向量库、数据库和多个外部工具，还可能持续流式返回结果。FastAPI 基于 ASGI，原生支持 async/await、流式响应和 WebSocket，能在等待外部 I/O 时继续处理其他请求；Pydantic 模型和 OpenAPI 又适合定义结构化输入输出与工具协议。它还方便接入依赖注入、认证、日志和 tracing。不过 FastAPI 只是服务层，长任务可靠执行、状态持久化、限流、重试和 CPU 密集计算仍需任务队列、数据库或独立 worker 配合。

它与 Agent 场景的匹配点

Agent 服务特点FastAPI 能力工程价值
大量等待 LLM / Tool / DBASGI + async/await等待时释放事件循环，提高 I/O 并发。
Token 持续产生StreamingResponse、SSE、WebSocket降低首字节延迟，支持实时进度与双向交互。
输入输出结构复杂Pydantic 校验与序列化让请求、工具参数和结构化输出拥有明确契约。
需要给客户端集成自动 OpenAPI 文档便于前后端联调，也可作为生成客户端的契约。
模型、租户、权限等横切关注点依赖注入、中间件、生命周期管理统一管理鉴权、客户端、连接池、配置、日志和 tracing。
部署需横向扩容无状态 HTTP 服务易复制 worker会话和任务状态外置后，可按流量水平扩容。

一次 Agent 请求怎么跑

POST /runs→校验输入→鉴权 / 限流→调用 LLM→调用 Tools→保存状态→SSE 流式返回
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/agents/{agent_id}/runs")
async def run_agent(agent_id: str, request: RunRequest):
    async def events():
        async for event in agent_service.stream(
            agent_id=agent_id,
            message=request.message,
        ):
            yield encode_sse(event)

    return StreamingResponse(events(), media_type="text/event-stream")

为什么不能只说“因为 FastAPI 快”

框架基准性能只是很小一部分。Agent 请求可能等待模型几十秒，真正决定体验和稳定性的通常是：

  • 是否使用异步 LLM、数据库和 HTTP 客户端；
  • 超时、取消、重试和幂等是否正确；
  • 是否限制每个租户和下游服务的并发；
  • 断线后能否恢复，流式输出是否有背压；
  • 会话、checkpoint 和运行状态是否持久化；
  • 是否能追踪每一步模型与工具调用的耗时、token、错误和成本。
FastAPI 不负责什么：进程内 BackgroundTasks 不等于可靠任务队列；Web 进程重启后任务可能丢失。分钟级或需要重试恢复的 Agent run，通常应交给 Celery、Dramatiq、Temporal 等外部 worker/工作流系统，状态放数据库或专门的 checkpoint store。

04 · 面试设计题：如何设计一个 FastAPI Agent 服务？

回答框架

  1. 接口层：创建 run、查询状态、取消 run、SSE/WebSocket 订阅事件。
  2. 编排层：维护模型调用、工具调用、循环上限、超时和状态机。
  3. 执行层：短请求可在 Web worker 中执行；长任务投递到可靠 worker。
  4. 状态层：run、message、tool result、checkpoint 放外部存储，不依赖单个进程内存。
  5. 治理层：认证、租户隔离、限流、预算、幂等键、工具权限与人工确认。
  6. 可观测性：trace 串起 HTTP → model → retrieval → tool；记录耗时、token、成本和错误类别。

线程、协程和进程怎么组合

工作放在哪里
异步调用 LLM、HTTP、异步数据库事件循环中的协程
暂时无法替换的同步 SDK受限线程池，避免阻塞事件循环
文档解析、重排序、纯 Python 计算进程池或独立 worker，按实测决定
本地 GPU 模型推理专门推理服务，不与 Web worker 混在一起
分钟级、需恢复的 Agent 工作流可靠任务队列或 durable workflow 引擎

06 · 地铁背诵版

GIL

常规 CPython 同一进程里，同一时刻通常只有一个线程执行 Python 字节码。它主要限制纯 Python CPU 任务的多线程并行，不妨碍 I/O 并发，也不等于线程安全。I/O 用 asyncio 或线程，CPU 用多进程或独立计算服务。

事件循环

协程运行到真正需要等待的 await 时主动让出，事件循环去运行其他就绪任务；I/O 完成后再恢复原任务。它解决的是大量 I/O 等待的并发效率，不会自动加速 CPU 计算。

FastAPI + Agent

Agent 服务要等待 LLM、数据库和工具，还需要流式输出。FastAPI 的 ASGI 异步模型、Streaming/WebSocket、Pydantic 和 OpenAPI 很匹配。但它只是接入层，可靠长任务、状态、限流、重试和 CPU 计算还需要外部组件。

一句话串联

Agent 大多在等 I/O，所以事件循环比堆线程更轻；FastAPI 把异步与流式能力暴露成服务；遇到 CPU 密集工作时，再考虑 GIL 并把计算移到进程或独立 worker。

07 · 高频追问

asyncio 是单线程，为什么还能处理高并发？
因为高并发请求的大部分时间在等待 I/O。一个任务等待时主动让出，同一线程就能推进其他任务。它提高的是等待阶段的利用率，不是单个请求的 CPU 执行速度。
async def 里面调用 requests 会怎样？
requests 是同步阻塞客户端，会卡住事件循环。优先换成异步客户端；无法替换时用受限线程池或 asyncio.to_thread()，并监控线程池饱和。
用了 asyncio 就完全不需要线程了吗？
不是。遗留同步 SDK、部分文件操作仍可能通过线程池承接。关键是不要让它们阻塞事件循环，并设置线程数和下游并发上限。
FastAPI 的 async 接口一定比 def 快吗？
不一定。只有内部使用真正的非阻塞 awaitable 才能发挥优势。同步路径可由框架放入线程池；CPU 密集代码无论写成 async 还是 def 都需要另行隔离。
一个 Agent 请求需要运行十分钟，直接保持 HTTP 连接可以吗？
可以流式保持，但可靠性通常不足。更稳妥的是创建 run 后返回 ID，由 durable worker 执行，客户端通过 SSE/WebSocket 或轮询订阅；服务重启、断线和重试后仍能从持久化 checkpoint 恢复。
如何防止一次请求并发调用几十个工具压垮下游？
在全局、租户、模型和具体工具等层级设置 Semaphore 或限流器，并配置连接池、超时、预算、队列长度和背压。并发不是越大越好，应由下游容量和延迟目标决定。
Agent 服务怎样做到幂等？
让客户端提供 idempotency key，服务端持久化 key 与 run/result 的绑定；重试时返回原 run 或结果。工具调用还要按业务语义单独设计幂等，不能只保证 HTTP 接口不重复创建任务。
GIL 会不会成为 FastAPI Agent 服务的瓶颈？
典型外部 LLM 编排主要受网络等待、下游限流和连接池影响，GIL 通常不是第一瓶颈。如果服务在本地做大量解析、压缩、重排序或纯 Python 计算，则需要 profiling，并把 CPU 工作移出 Web 事件循环和进程。

08 · Java：现有 Spring Boot RAG 服务怎么对接大模型 Agent？

30 秒面试回答

如果 Spring Boot 已经实现了 RAG，我通常不会把整套 RAG 逻辑重新塞进 Agent，而是把它封装成一个边界清楚的检索 Tool。Agent 根据用户问题决定何时调用，Spring Boot 负责权限过滤、向量检索、重排和返回带来源的 chunks，Agent 再结合结果生成答案。检索这一步在业务语义上是同步依赖，因为 Agent 拿不到结果就无法继续推理；但在程序实现上，我会优先使用非阻塞异步 HTTP。面向用户，普通问答使用 SSE 流式响应；需要多轮工具调用、耗时长或必须可恢复的任务，则采用异步 run：先返回 runId，后台执行，再通过 SSE、轮询或回调获取进度和结果。

先确定谁是编排者

“Spring Boot 对接 Agent”实际上有两种方向，不能一上来只讨论 HTTP 客户端。

模式调用方向适合场景
RAG 作为 Agent Tool（推荐起点）Agent → Spring Boot RAG已经有独立 Agent 编排层；Java 服务拥有文档、权限和检索逻辑。
Spring Boot 作为业务入口Client → Spring Boot → AgentJava 服务负责用户、会话、鉴权和业务接口，Agent 是下游能力。
Spring Boot 内嵌 AgentJava 进程内完成模型与工具编排团队希望统一 Java 技术栈，可使用 Spring AI、LangChain4j 或自研编排。
对“现有 RAG 服务”最自然的改造：先把它作为 Tool 保留。Agent 管“什么时候检索、是否继续调用其他工具”，Spring Boot 管“去哪里检索、权限怎么算、返回哪些可靠证据”。这样领域边界清楚，也避免复制知识库逻辑。

推荐架构：把 RAG 暴露成检索工具

用户问题→Agent 判断是否检索→调用 RAG Tool→Spring Boot 鉴权 + 检索 + 重排→返回 chunks + sources→Agent 生成答案

工具接口建议返回“证据”，而不是直接返回一段已经生成好的最终答案。否则 Agent 很难判断来源、做多工具融合或控制引用。

同步还是异步？先拆成三层

面试里最容易答错，是把“业务步骤是否要等结果”“Java 代码是否阻塞线程”“HTTP 是否立即返回结果”混成同一个概念。

层次推荐判断解释
Agent → RAG 的业务依赖通常逻辑同步Agent 必须拿到检索结果才能继续生成；代码里表现为 await、Mono 或 Future，并不等于阻塞线程。
Java HTTP 客户端实现高并发/流式优先非阻塞异步WebClient 能在等待 Agent、模型或 RAG 时释放线程；低并发内部服务使用同步客户端也可以，先看复杂度和容量。
面向用户的 API 协议按任务时长选择短任务同步返回；交互问答多用 SSE 流式；长任务使用 runId 异步任务模式。

三种调用方式怎么选

方式接口形态适用范围注意点
同步请求/响应POST /chat 直接返回 JSON单次 RAG、耗时短、无需中间进度设置整体和下游超时；连接断开会影响体验。
SSE 流式响应POST /chat/stream 返回 token/event在线问答、逐步展示模型输出和工具状态处理断线、取消、心跳、代理缓冲和背压。
异步任务POST /runs → 202 + runId多轮 Agent、报告生成、批量检索、分钟级任务需要任务队列、状态机、幂等、持久化、重试、查询和取消接口。
实战推荐：在线聊天默认用 SSE，但同时把每次执行建模为 run 并持久化。这样正常情况实时流式返回，客户端断线后仍能凭 runId 查询或恢复，而不是把可靠性押在一条 HTTP 长连接上。

Spring Boot 调 Agent：WebClient 流式示例

@Service
public class AgentClient {
    private final WebClient webClient;

    public AgentClient(WebClient.Builder builder) {
        this.webClient = builder.baseUrl("http://agent-service").build();
    }

    public Flux<ServerSentEvent<String>> stream(AgentRequest request) {
        return webClient.post()
            .uri("/agents/order-assistant/runs/stream")
            .bodyValue(request)
            .retrieve()
            .bodyToFlux(new ParameterizedTypeReference<>() {});
    }
}

如果 Controller 也返回 Flux，数据可以边到边转发，不需要先把完整结果放进内存。生产环境还要补充连接超时、响应超时、重试条件、最大响应大小、trace header 和客户端断开后的取消传播。

Spring MVC、WebFlux 怎么选

  • 现有项目是 Spring MVC：不必为了“接 Agent”强行全量改成 WebFlux。低到中等并发可使用同步客户端；流式接口也可用 SseEmitter。如果大量长连接和外部等待成为瓶颈，再基于压测演进。
  • 大量 SSE、WebSocket 或 I/O fan-out：WebFlux + WebClient 更自然，但要求整条主要调用链避免同步阻塞。
  • Java 虚拟线程：可以降低阻塞式 I/O 的线程成本，让同步代码保持直观；但不会让下游变快，也不能替代限流、超时、背压和可靠任务系统。
  • @Async：只是把工作提交到另一个线程池，不等于非阻塞 I/O，也不等于可靠异步任务。进程重启、队列满和任务重试仍需额外设计。

接口契约里必须考虑什么

  • 权限上下文：tenant、user、角色和文档 ACL 必须传入 RAG，并在服务端强制过滤，不能只靠 Prompt。
  • 来源与版本：返回 documentId、source、score、文档版本和检索策略版本，方便引用与复现。
  • 超时预算：区分整个 run、单次模型和单个工具的 timeout；不要无限重试。
  • 幂等：创建 run 和有副作用的 Tool 分别设计 idempotency key。
  • 可观测性：统一 traceId，串联 Spring Boot、Agent、LLM、向量库和工具调用。
  • 防提示词注入：检索文档是不可信输入；工具权限、参数校验和副作用确认必须在代码层实现。

什么时候不该让 Agent 直接调用 RAG？

如果每个请求都必须检索、流程固定且不需要 Agent 决策，普通的 RAG pipeline 可能更简单：query → retrieve → rerank → prompt → answer。只有需要动态决定是否检索、改写查询、调用多个知识源或工具、根据中间结果继续推理时，Agent 编排才真正有价值。

面试加分点：不要回答“统一用异步，因为性能高”。更好的说法是：RAG 对 Agent 通常是一个必须等待的逻辑同步步骤；代码实现可以非阻塞；用户协议则根据时长选择 JSON、SSE 或 runId 异步任务。三层含义不同。

地铁背诵版

现有 Spring Boot RAG 最适合封装成 Agent Tool：Java 服务负责权限、检索和重排，返回带来源的 chunks；Agent 负责决定何时调用以及如何组织答案。Agent 调 RAG 在业务上要等结果，所以是逻辑同步，但网络实现可以用 WebClient 非阻塞。短问答直接同步，聊天用 SSE，长时间多步骤任务用 runId + 后台 worker。不要把 @Async 当成可靠任务队列，也不要为了异步强行把整个 Spring MVC 项目改成 WebFlux。

09 · Redis 在 Agent 系统里能做什么？

30 秒面试回答

Redis 在 Agent 系统里适合承载高频访问、允许过期、需要原子操作的热状态，例如会话上下文缓存、运行状态、限流计数、并发租约、幂等键、短期工具结果缓存和流式事件。以会话为例，我会把最近消息、摘要、当前 run 和 TTL 放 Redis，完整消息和审计记录仍落数据库；以限流为例，不只限制请求次数，还会按用户、租户、模型分别限制 RPM、TPM 和并发 run，并使用 Lua 脚本保证判断与扣减原子执行。Redis 是高速协调层，不应该默认成为所有长期记忆的唯一事实源。

Agent 系统中的常见用途

用途例子为什么适合 Redis
会话热上下文最近 N 条消息、滚动摘要、当前工具状态读写频繁、低延迟、天然适合 TTL。
运行状态与 checkpointqueued/running/waiting_tool/completed前端频繁查询；可配合数据库保存耐久事实。
请求与 Token 限流用户 RPM、租户 TPM、模型 QPSINCR、ZSET 和 Lua 支持原子计数。
并发控制单租户最多 10 个活跃 run带过期租约可防 worker 异常造成永久占位。
幂等与去重同一 Idempotency-Key 只创建一个 runSET NX EX 可原子占位并自动过期。
结果与语义缓存相同检索条件、Embedding 或工具查询短期复用降低下游延迟和费用，但必须纳入权限与版本。
事件分发token、tool_started、tool_finished、errorPub/Sub 适合在线广播；Streams 适合需要确认和一定保留的消费。
分布式协调避免同一会话被两个 worker 同时推进可使用租约锁，但必须设计超时、续租和 fencing。
边界：Redis 很快，但内存昂贵且数据可能因淘汰、过期或故障丢失。完整聊天记录、合规审计、计费流水、关键 checkpoint 通常还要落 PostgreSQL/MySQL 或其他持久化存储；长期语义记忆通常进入向量库或带向量能力的持久化系统。

例一：Redis 怎么存会话上下文？

先区分三种数据，不要把“Agent memory”全部塞进一个 JSON：

数据建议位置说明
最近对话与当前运行状态Redis 热缓存组装 Prompt 时频繁读取，设置空闲 TTL。
完整消息、工具调用、审计记录关系数据库/持久化日志用于恢复、审计和问题复现，是耐久事实源。
跨会话长期记忆和知识数据库 + 向量索引经过抽取、授权和生命周期治理后检索，不应无限拼进 Prompt。

推荐 Key 设计

# 会话元数据：Hash
agent:session:{tenantId}:{sessionId}:meta
  user_id       = u-123
  agent_id      = order-assistant
  summary       = 用户正在处理订单 O-88 的退款问题……
  summary_seq   = 120
  active_run_id = run-456
  version       = 19

# 最近消息：List 或 Stream
agent:session:{tenantId}:{sessionId}:messages
  [{seq:121, role:"user", content:"……"},
   {seq:122, role:"assistant", content:"……"}]

# 单次运行热状态：Hash
agent:run:{tenantId}:{runId}
  status       = waiting_tool
  current_step = search_order
  updated_at   = 1788200000

# 建议：会话空闲 24 小时过期，run 按业务保留 1～24 小时
EXPIRE agent:session:{tenantId}:{sessionId}:meta 86400
EXPIRE agent:session:{tenantId}:{sessionId}:messages 86400

一次请求如何读取和写入

校验 tenant/user→读取 summary + 最近消息→按 token 预算裁剪→调用 Agent→持久化完整事件→更新 Redis 热窗口
  1. 用 tenantId + sessionId 构造 Key，先验证用户是否有权访问，不能只凭客户端传来的 sessionId。
  2. 读取滚动摘要和最近若干消息，按 token 预算组装，而不是固定取“最近 20 条”。
  3. 新消息先写耐久存储或可靠事件流，再更新 Redis；不能因 Redis 更新成功就认为消息已永久保存。
  4. 消息过长时异步生成新摘要，并用 version 或 CAS/Lua 防止并发请求互相覆盖。
  5. 每次访问刷新空闲 TTL；删除会话时同时清理关联 Key，或使用统一前缀和索引管理。

为什么要“摘要 + 最近消息”

假设一个会话已有 500 条消息，全部送给模型会增加 token 成本、延迟并稀释注意力。可以保留：

  • 稳定事实摘要：用户目标、已确认约束、关键业务实体；
  • 最近消息窗口：保留当前语境和指代关系；
  • 按需检索记忆：历史细节需要时再从持久化消息或向量索引取回。
常见错误：只用 sessionId 做 Key 导致跨租户碰撞；把完整会话永远放 Redis；每次把所有历史消息塞进 Prompt；并发更新摘要时没有版本控制；Redis 淘汰后无法从数据库恢复。

例二：Agent 系统怎么做限流？

Agent 的成本不仅是“请求数”。一次请求可能循环调用多次模型和工具，因此至少考虑四个维度：

维度Key 示例保护对象
请求频率 RPMrl:rpm:{tenant}:{user}:{minute}防止接口被突发请求打满。
Token 配额 TPMrl:tpm:{tenant}:{model}控制模型吞吐和费用。
活跃 run 并发rl:concurrent:{tenant}限制同时执行的长任务。
工具级 QPSrl:tool:{tenant}:{tool}保护数据库、搜索、支付等具体下游。

方案 A：固定窗口，简单但有边界突刺

-- KEYS[1] = rl:rpm:{tenant}:{user}:202609011230
-- ARGV[1] = limit, ARGV[2] = ttlSeconds
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return {0, current}
end
return {1, current}

判断和设置 TTL 必须放在同一个 Lua 脚本里，否则应用在 INCR 后崩溃可能留下永不过期的 Key。固定窗口实现便宜，但用户可以在两个窗口交界处瞬间打出接近两倍流量。

方案 B：滑动窗口，频率更准确

用 ZSET 保存最近窗口内的请求时间戳，并在 Lua 中原子执行：

1. ZREMRANGEBYSCORE key 0 (now - window)
2. ZCARD key
3. 如果 count >= limit：拒绝并返回 retryAfter
4. 否则 ZADD key now uniqueRequestId
5. EXPIRE key window + buffer

它比固定窗口平滑，但每次请求都需要维护成员，内存和操作成本更高。大规模系统也可使用近似滑动窗口或网关限流。

方案 C：Token Bucket，适合模型 Token 和突发流量

Bucket 保存 tokens 和 last_refill_time。每次请求根据经过时间补充 token，再尝试扣减。Lua 保证“补充、判断、扣减”原子完成。

LLM Token 的特殊处理：请求前只能估算输出 token。可以先按“输入 token + max_output_tokens”预占额度，请求完成后按实际 usage 结算并返还差额。流式请求中也可以定期结算，防止长输出突破预算。

并发 run：用带租约的信号量

不能简单 INCR 后等任务结束再 DECR，因为 worker 崩溃会永久占用名额。更稳妥的是使用 ZSET：

# member = runId, score = leaseExpireAt
1. 删除 score < now 的过期 run
2. 检查 ZCARD 是否小于并发上限
3. 允许则加入 runId 和租约到期时间
4. worker 运行期间续租，完成或取消时删除

# 上述 1～3 步必须在 Lua 中原子执行

Spring Boot 中的调用位置

认证→限流 Lua→创建/恢复 run→Agent 执行→实际 Token 结算→释放并发租约
  • 通用 HTTP RPM 可以放在 API Gateway；租户、模型、工具和 token 规则通常更懂业务，应放在 Agent 服务内部。
  • 限流返回 429，附带 Retry-After、limit、remaining 和 reset 时间，便于客户端退避。
  • 限流 key 需要散列用户或租户标识，避免把手机号等敏感信息直接暴露在 Redis 运维界面。
  • Redis 异常时选择 fail-open 还是 fail-closed 要按风险决定：普通聊天可降级，付费额度和高风险工具通常宁可拒绝。

会话和限流结合的完整例子

用户向订单 Agent 提问时：

  1. 网关检查用户基础 RPM；Agent 服务检查租户 TPM 和活跃 run 数。
  2. 通过后，用幂等键创建 run，并从 Redis 加载会话摘要和最近消息。
  3. Agent 调用 RAG 和订单工具；每种工具还有独立并发和 QPS 限制。
  4. SSE 持续推送事件，同时将完整消息和工具调用写入数据库。
  5. 完成后更新 Redis 会话热窗口、结算实际 token、释放 run 租约。
  6. 若连接断开，run 状态仍可通过数据库或可靠 worker 恢复，Redis 只负责快速查询和协调。

地铁背诵版

Redis 在 Agent 系统里主要做热状态和分布式协调：会话上下文缓存、run 状态、限流、并发租约、幂等和短期缓存。会话一般保存滚动摘要加最近消息并设置 TTL，完整记录仍落数据库。限流不能只看请求数，还要按用户和租户控制 RPM、模型 TPM、活跃 run 和工具 QPS；判断与扣减用 Lua 保证原子性，长任务的并发名额要使用可过期、可续租的租约。Redis 是高速协调层，不是所有长期记忆的唯一事实源。
