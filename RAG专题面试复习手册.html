Q01基础与架构简单

什么是 RAG 检索增强生成？它解决了大模型的哪些问题？

记忆路线查资料 → 带证据 → 再生成
一句话抓重点

RAG 是先检索外部证据，再让模型基于证据回答。

口述答案 约 45–90 秒 · 按语速与追问深度调整

RAG 的全称是 Retrieval-Augmented Generation，检索增强生成。它在回答前，从外部知识源检索与问题相关的信息，再把这些信息作为上下文交给模型组织答案。

它主要缓解三个问题：模型不了解企业私有知识、参数中的知识更新不及时，以及回答缺少可核验依据。更新知识库往往比重新训练模型更方便，也能给答案提供引用。

但 RAG 不保证没有幻觉。知识源错误、检索漏召回、上下文冲突或模型没有忠实使用证据，都可能导致错误，所以还需要评估、引用核验和无依据时的拒答。

原理、例子与追问 2 个要点
  • 例子：问“新款产品退货期限”，系统先检索对应型号和生效版本的售后政策，再回答并附条款来源。
  • RAG 不必只用向量检索；关键词、数据库查询、知识图谱和外部搜索都能成为检索来源。
容易答错

RAG 通常不改变生成模型的权重；“接入 RAG 就能消除幻觉”是错误表述。

Q02基础与架构简单

RAG 的完整工作流程是怎样的？核心步骤有哪些？

记忆路线采集 → 解析 → 分块 → 索引；检索 → 重排 → 生成 → 验证
一句话抓重点

完整链路分为离线建库和在线问答，两端共同决定质量。

口述答案 约 45–90 秒 · 按语速与追问深度调整

离线阶段先采集文档、解析格式、清洗去重，再按结构分块，保留来源、版本、页码和权限等元数据；用 Embedding 模型生成向量，连同文本和元数据写入检索系统。

在线阶段先确认用户身份与查询范围，必要时改写问题，再进行向量或混合检索。对候选结果过滤、去重和重排后，按上下文预算组织证据，交给模型生成带引用的回答。

最后核验引用与关键事实，并记录检索、生成、耗时和成本。知识更新、权限变更和 bad case 回流也属于生产闭环，不能只画“问题到向量库到模型”三个框。

原理、例子与追问 2 个要点
  • 最简可用版本可以没有查询重写或 rerank；它们是按问题增加的优化模块，不是每次都必须调用。
  • 关键排错顺序：知识是否入库 → 正确块是否召回 → 是否排进上下文 → 模型是否用对。

Q05基础与架构简单

RAG 和模型微调 Fine-tuning 有什么区别？如何选择？

记忆路线知识放外部 → 行为调参数 → 按瓶颈选
一句话抓重点

RAG 主要补充可更新知识；微调主要改变模型在目标任务上的行为，两者可以组合。

口述答案 约 45–90 秒 · 按语速与追问深度调整

RAG 在推理时提供外部上下文，通常不修改模型权重，适合知识频繁更新、需要引用、权限分隔或企业私有资料问答。微调通过训练调整模型参数，更适合稳定输出格式、领域表达、指令遵循或特定任务能力。

如果问题是模型不知道新政策，我先补知识与检索；如果证据已正确提供，但模型持续不能按要求抽取字段或组织答案，再考虑高质量样本微调。微调并不是不能学习知识，而是不适合作为频繁、精确更新事实的唯一手段。

两者也能配合，例如微调检索模型改善领域召回，再用 RAG 提供实时知识，或者训练生成模型更忠实地使用检索证据。

原理、例子与追问 2 个要点
  • 选择前先建立基线：提示词、检索和数据清洗是否已经足够；微调要计算数据标注、训练和版本维护成本。
  • 知识进入模型参数后，定点纠错、删除与按用户权限隔离一般更难。

不要把 RAG 和微调说成互斥，也不要承诺微调后就不需要事实核验。

Q30基础与架构简单

什么是 RAG？RAG 的主要流程是什么？

记忆路线定义 → 离线 → 在线 → 边界
一句话抓重点

一句定义加两条流程：离线建知识索引，在线检索后生成。

口述答案 约 45–90 秒 · 按语速与追问深度调整

RAG 是让模型在回答前检索外部资料，并将相关证据加入上下文的生成方式。可以把它理解为“先查资料，再结合问题作答”。

离线流程是采集、解析清洗、分块、向量化和建索引；在线流程是处理问题、在授权范围内检索、筛选证据、组织 Prompt、生成答案并附引用。

例如售后问答先检索适用版本的政策，再给出条件和来源。它能补充私有与最新知识，但效果依赖资料质量、召回质量和模型对证据的使用，不能保证自动消除幻觉。

原理、例子与追问 2 个要点
  • 这道是快速概括题，先控制在约 45 秒；面试官追问时再展开第 2 题的完整工程链路。
  • 分清知识解释与实时业务查询：退款是否到账应查业务接口，不靠静态文档推断。
容易答错

不要把定义讲成“把数据库里的所有资料一次性放进 Prompt”。

RAG 的完整流程是怎么样的？

把 RAG 讲成一个含更新、检索、生成和评测的闭环。

口述答案 约 45–90 秒 · 按语速与追问深度调整

我会画两条主线。入库线：数据源接入、解析清洗、分块和元数据、Embedding、向量与词项索引。问答线：身份与问题处理、检索与融合、重排筛选、上下文组装、生成与引用核验。

  • 追问“哪里存什么”：原文存档、向量与元数据、任务日志和评测集各有职责。

Q52基础与架构中等

什么是 Advanced RAG？

记忆路线检索前优化 → 检索优化 → 检索后优化
一句话抓重点

Advanced RAG 是在基础检索生成流程前后，增加有针对性的质量优化。

口述答案 约 45–90 秒 · 按语速与追问深度调整

Advanced RAG 一般指相对基础 RAG 增加检索前、检索中和检索后的优化。检索前可以做数据清洗、结构化分块、查询改写和元数据限定；检索中可用混合召回与更合适的索引；检索后可做重排、去重、上下文压缩和证据筛选。

它的目标是减少简单“切块、向量检索、拼 Prompt”流程的盲区，让证据更相关、上下文更有效。不同项目需要的组合不同，并没有一张必须全部勾选的组件清单。

我会先按评测定位瓶颈，再增加对应模块，每一步验证收益和成本。如果简单方案已经达标，就没有必要为了名称而堆复杂度。

原理、例子与追问 2 个要点
  • 例如正确证据在候选里但排得靠后，加入 rerank 比直接换生成模型更对症。
  • 这是常见架构分类，不是某个框架的唯一 API 或统一行业认证。
容易答错

Advanced 不意味着一定要多 Agent、知识图谱或多次大模型调用。

RAG 中如何计算文本相似度？常见算法有哪些？

一句话抓重点

口述答案 约 45–90 秒 · 按语速与追问深度调整

词项方法包括 TF-IDF 向量配合余弦相似度，或用 BM25 给查询与文档打相关性分数；它们擅长专有词和精确匹配。语义检索则先生成 Embedding，常用余弦相似度、点积和欧几里得距离。

余弦看方向，点积同时受方向与长度影响，欧氏距离看空间直线距离。对单位归一化向量，点积等于余弦，而且欧氏距离平方等于 2 减 2 倍余弦，因此排序具有对应关系。

我会遵循模型建议的度量和归一化方式，并用业务检索集验证。相似度分数是排序信号，不是答案正确的概率。

原理、例子与追问 2 个要点
  • 余弦公式：cos(q,d)=q·d/(‖q‖₂‖d‖₂)。零向量不能直接按该式计算。
  • BM25 是词项相关性评分，不是稠密向量距离；不同检索器原始分数不要直接相加。
展开相似度公式
cos(q,d) = (q · d) / (‖q‖₂ ‖d‖₂)
dot(q,d) = Σ qᵢdᵢ
L2(q,d) = √Σ(qᵢ−dᵢ)²
单位归一化时：L2² = 2 − 2cos

公式中的余弦要求非零向量；返回分数是否经过映射，要看具体 API。

有些 API 返回 distance，越小越好；有些返回 similarity，越大越好，不能把阈值方向写反。

Q50Embedding 与相似度中等

向量数据库中，常见的向量搜索方法：余弦相似度、欧几里得距离和曼哈顿距离分别是什么？有什么区别？

一句话抓重点

余弦比较方向，欧氏距离比较直线差异，曼哈顿距离累计各维绝对差。

口述答案 约 45–90 秒 · 按语速与追问深度调整

余弦相似度是两向量点积除以各自的 L2 范数，主要反映方向，非零向量分数越大越相似。欧几里得距离是各维差值平方和再开根号，反映空间直线距离，越小越近。曼哈顿距离是各维绝对差之和，也叫 L1 距离。

欧氏距离和曼哈顿距离都会受坐标尺度影响，前者对较大的单维偏差相对更敏感。对单位归一化向量，欧氏距离平方与余弦满足 2−2cos 的关系，因此排序等价；曼哈顿没有这一普遍对应关系。

实际选择跟随模型训练与索引支持的度量，再做验证。文本向量中不能因为某种距离公式熟悉，就随意替换模型推荐方式。

原理、例子与追问 2 个要点
  • 例子 q=(1,0)、d=(2,0)：余弦为 1，但 L2 和 L1 都为 1，说明方向一致不等于坐标相同。

不要说余弦在所有场景都优于欧氏距离；也不要忘记余弦对零向量未定义。

向量数据库原理是什么？ 请简述下它的原理

  • 标量过滤与 ANN 的执行次序会影响召回和效率，应按查询分布验证。

向量数据库不是先计算并保存所有向量两两之间的距离矩阵。

Q47向量库与索引中等

向量数据库中的 HNSW、LSH、PQ 分别是什么意思？

记忆路线图找近邻 → 哈希找桶 → 子空间量化
一句话抓重点

HNSW 是图索引，LSH 是局部敏感哈希方法，PQ 是向量压缩技术。

口述答案 约 45–90 秒 · 按语速与追问深度调整

HNSW 是 Hierarchical Navigable Small World，通过多层近邻图加速搜索，通常以较高内存和构建成本换取查询性能。LSH 是 Locality-Sensitive Hashing，设计哈希函数让相近向量更容易落进同桶，查询时从相关桶中找候选；具体哈希方案依距离定义选择。

PQ 是 Product Quantization，把向量分成多个子空间，各自用码本量化，只保存较短的编码，查询时通过查表近似计算距离。它的重点是减少存储和计算，也会引入量化误差。

三者不是完全同层的互斥选项，例如 IVF 可以与 PQ 结合。选型需要看内存、吞吐、召回和更新，而不是把名称当成固定排名。

原理、例子与追问 2 个要点
  • LSH 不同于普通哈希表：它主动提高相似对象发生哈希碰撞的概率。
  • PQ 码本通常需要训练；保留原向量用于后续精排可以缓解部分量化误差。

名称核心思想所属层次
HNSW多层近邻图，逐层定位候选近邻索引／搜索结构
LSH相近向量高概率哈希到同桶候选生成方法家族
PQ拆子空间、训练码本、短码表示压缩与近似距离计算技术
容易答错

不能说 PQ 本身就是“图检索算法”，也不要认为所有组合都被所有向量库支持。

向量数据库中的 ANN 是什么？为什么需要用它？

记忆路线精确成本 → 近似候选 → 召回权衡 → 对照基线
一句话抓重点

ANN 用可接受的近邻遗漏换取更低的查询代价，适合大规模相似搜索。

口述答案 约 45–90 秒 · 按语速与追问深度调整

这里 ANN 指 Approximate Nearest Neighbor，近似最近邻，不是人工神经网络。精确搜索需要按选定度量检查全部向量，单个查询的基础计算量约随向量数 N 和维度 d 增长，即 O(Nd)。

  • ANN Recall@K 常指与精确向量 top-K 的重合率；业务检索 Recall@K 指对标注相关证据的覆盖，二者不是同一指标。
  • 索引逼近得很准，也可能因为 Embedding 不适合业务而召回错误内容。
容易答错

精确向量最近邻也不等于语义上绝对正确，更不等于能支持答案。

RAG 检索中的 Top-K 是什么意思？K 值如何确定？

一句话抓重点

Top-K 是保留排名最靠前的 K 个候选，召回 K 和最终上下文 K 要分开调。

口述答案 约 45–90 秒 · 按语速与追问深度调整

Top-K 表示从检索结果中返回排名最高的 K 个文档块。K 小时延迟低、噪声少，但可能漏掉关键证据；K 大通常提高候选覆盖，却会增加重排成本、重复内容和上下文干扰。

我会区分三个量：各路召回的候选数、融合后送入 rerank 的数量、最终交给生成模型的证据数。它们不必相同。例如可以把 20、50、100 作为候选数的实验档位，再从中选少量高质量证据进入上下文。

选择时同时看 Recall@K、重排后排序质量、答案正确率和 P95 时延，并受模型上下文预算约束。不同任务也可动态选择 K，但动态策略本身需要评测。

原理、例子与追问 2 个要点
  • K 只是数量上限，不是相关性保证；没有合格证据时应少返或不返，而不是凑满 K 条。
  • 多跳问题需要多份证据，单事实问答可能只需一两块；相邻重复块应去重。
容易答错

示例档位只是实验起点，不是通用最佳参数；增大 K 不能修复知识缺失。

元数据限定可检索的业务范围，权限过滤还必须由服务端强制执行。

口述答案 约 45–90 秒 · 按语速与追问深度调整

元数据可以包括租户、文档类型、产品型号、语言、版本、生效时间、部门和访问范围。用户问某型号的现行政策时，先限定型号和有效版本，能减少语义相似但不适用的资料。

元数据本身如果错误或过期，会造成误召和漏召；权限撤销也要影响缓存与历史引用。

重写器输出是检索输入，不是可信事实，也不能生成或覆盖用户权限。

RAG 为什么需要重排序 Reranking？如何实现？

记忆路线宽召回 → 精打分 → 去冗余 → 选证据
一句话抓重点

Reranking 对已召回候选做更精细的相关性判断，提高送入模型的证据质量。

口述答案 约 45–90 秒 · 按语速与追问深度调整

第一阶段检索强调在大规模数据中快速找到可能相关的候选，但向量近似搜索和单个相似度分数不一定能准确判断细粒度条件。重排序在较小候选集合上使用更精细的模型，提高相关内容的排序位置。

常见方式是 Cross-Encoder，把 query 和文档一起输入模型，得到相关性分数；也可用专门 reranker 或受约束的大模型打分。对候选批量评分后排序，再结合去重、证据覆盖和上下文预算选择结果。

我会同时评估排序指标、答案正确率和重排耗时。长候选可能被模型截断，需要控制长度；规模太大的候选集合也会带来较高成本。

原理、例子与追问 2 个要点
  • 双编码器可预计算文档向量，适合第一阶段；Cross-Encoder 联合看 query 与文档，通常更贵，适合候选精排。
  • 重排分数不一定是校准概率，也不直接代表文档是否事实正确。
容易答错

正确文档没有进入候选集时，重排序无法凭空找回来。

口述答案 约 45–90 秒 · 按语速与追问深度调整

这里的自查询通常指 Self-Query Retrieval：系统从用户请求中提取语义检索文本和元数据条件。例如“找 2025 年发布、针对 X20 的维修指南”，可以拆出查询“维修指南”，以及年份和型号过滤。

它减少纯向量检索对明确条件的忽视。但来自登录态的租户和权限必须在服务端强制加入，与生成的业务条件取交集，不能由模型决定。

原理、例子与追问 2 个要点
  • 如果文档没有可靠的年份或型号元数据，再好的自查询也无法正确过滤。
  • 查询返回条数可以作为单独受限参数处理，避免模型构造过大的检索请求。
容易答错

自查询不是模型自动给自己回答，也不是让模型任意生成 SQL 或权限条件。

一句话抓重点

口述答案 约 45–90 秒 · 按语速与追问深度调整

提示压缩是对将要送入模型的上下文进行裁剪、抽取或压缩，在预算内保留与问题相关的关键信息。RAG 检索结果可能很长、重复或含无关段落，直接全塞进去会增加成本并干扰回答。

原理、例子与追问 2 个要点
  • 对多轮对话做查询压缩，与对检索文档做上下文压缩是不同位置的处理。
  • 可先保留关键原文片段和来源，再压缩重复解释，而不是把原文完全替换为无出处摘要。
容易答错

提示压缩不是模型量化，也不是缩短提示词就一定提高准确率。

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.rag.Query;
import org.springframework.ai.rag.preretrieval.query.transformation.RewriteQueryTransformer;

// 放入你的服务类；modelClient 应连接已配置好的 ChatModel。
static Query rewriteForSearch(
        ChatClient.Builder modelClient, String userQuestion) {
    if (userQuestion == null || userQuestion.isBlank()) {
        throw new IllegalArgumentException("question must not be blank");
    }
    var rewriter = RewriteQueryTransformer.builder()
            .chatClientBuilder(modelClient)
            .build();
    return rewriter.transform(new Query(userQuestion));
}

Spring AI 的模块化 RAG 受已有 Modular RAG 概念启发。预检索阶段处理 Query，可做重写、翻译、历史压缩或多查询扩展；检索阶段通过 DocumentRetriever 获取候选，用 DocumentJoiner 合并多查询、多来源的文档。

后检索阶段用 DocumentPostProcessor 对候选重排、去冗余或压缩。接下来由 QueryAugmenter 将证据补充到查询上下文，再交给模型生成。RetrievalAugmentationAdvisor 可把相关模块接入 ChatClient 流程。

我会明确每个模块的输入输出、预算和版本，针对瓶颈替换模块。权限条件必须由可信服务端构造，不能允许模型或客户端通过动态参数覆盖强制过滤。

  • ConcatenationDocumentJoiner 的拼接去重不等于自动进行 RRF 或模型重排；需要相应实现。
  • 默认不允许空上下文回答是提示层行为；如果业务必须严格拒答，可以在模型调用前加确定性分支。
