AI Agent 工程化开发

根据下载目录中 77 个 HTML 课程页面整理。重点不是某个工具按钮怎么点，而是如何把 AI 编程从“聊天生成代码”升级为可规划、可验证、可持续、可自主运行的工程系统。

01 · 一句话理解整门课

高质量 AI 编程的关键，不是写出一条“神 Prompt”，而是把需求、上下文、代码结构、反馈循环、权限边界和任务队列组合成一个 Agent 能稳定工作的系统。

人的核心价值是提供目标、品味和判断；AI 的核心价值是承担探索、实现和重复劳动。

研究 / 原型→PRD→Issues / Plan→Agent 实现→自动反馈→人工 QA→新 Issue
目标一：可控让 Agent 明白做什么、不做什么、如何判断完成。
目标二：可信用类型、测试、格式化和人工 QA 提供真实反馈。
目标三：可扩展把大任务切成小任务，让每个上下文只处理一个清晰单元。
目标四：可自主任务足够明确且防护到位后，让 Agent 在沙箱中 AFK 执行。

02 · 先接受 LLM 的四个约束

2.1 注意力不是无限的

上下文窗口的“最大容量”不等于模型始终能高质量处理的容量。课程将前段称为 smart zone，将信息过多后推理明显变差的区域称为 dumb zone。因此，更大的上下文窗口并不能替代上下文管理。

2.2 幻觉是缺少清晰信息时的合理补全

模型不是数据库。它可能发明不存在的方法、记错新版本 API，或者按旧知识编写代码。重要文档、真实类型定义、现有用法和版本信息应该放进当前上下文，并通过运行代码验证。

2.3 Agent 是无状态的新员工

每次新会话都像一位刚加入项目的工程师。它没有人类长期维护代码库形成的“肌肉记忆”，所以仓库能否快速被探索、模块边界是否清晰、约定是否显式，直接决定 Agent 的表现。

2.4 知识存在截止日期

新框架、新 SDK 和新服务不能只依赖模型记忆。应当查询当前官方资料，必要时整理成临时研究文档，供后续多个任务复用。

工程含义：不要把失败简单归咎于模型“不够聪明”。先检查它是否拿到了正确上下文、任务是否过大、反馈是否充分、代码库是否难以理解。

03 · 日常操作与会话管理

课程前半部分先建立基本操作习惯：引用文件、运行 Bash、观察工具调用、连接 IDE、回退变更、暂停和恢复会话，以及配置权限。

能力用途注意点
@文件 引用明确把计划、PRD 或代码放入上下文优于含糊地说“看一下那个文件”
Bash 命令检查仓库、运行测试和开发服务长时间服务与一次性命令要区分
IDE Diff直观看改动、接受或拒绝局部修改适合人工审查，不等同于测试
Rewind / Git回到之前状态或恢复会话Git 保护代码历史，不能代替权限隔离
权限规则减少重复确认只放行精确命令，避免过宽通配符

课程项目还通过专门的状态行显示上下文使用量，目的不是追求精确百分比，而是让“上下文预算”成为执行决策的一部分。

04 · 上下文管理：Plan → Execute → Clear

4.1 Plan Mode 做什么

Plan Mode 限制写文件能力，让 Agent 主要做读取、探索、运行只读命令、询问需求和形成计划。它的价值有两层：

  • 逼迫人把含糊想法变成明确决策；
  • 让 Agent 在写代码前理解现有架构和约束。

4.2 推荐循环

  1. Plan：从短需求开始，让 Agent 探索代码，并要求它“把每个设计决定都问清楚”。
  2. Execute：确认计划后实现，持续观察类型检查、测试和上下文消耗。
  3. QA：真实运行功能，用不同角色和边界条件测试。
  4. Clear：完成一个独立单元后清空上下文，用持久化的计划和代码进入下一轮。

如果规划结束时上下文仍很轻，可以保留讨论中丰富的决策信息继续实现；如果已经接近高负荷区，应清空后用计划文件重新开始。这里没有机械阈值，核心是给调试和迭代预留空间。

4.3 Compaction 的风险

自动压缩会把早期对话总结成更短内容，但反复压缩会形成“沉积层”：细节丢失、过时信息保留、摘要继续被摘要。重要决定应落到 PRD、计划、Issue、测试和代码中，而不是依赖对话历史。

4.4 Subagent 的真正意义

子 Agent 首先是一种上下文隔离机制：让探索、研究等任务在独立窗口大量工作，只把结论摘要交回主 Agent。它也可以并行，但并行不是唯一目的。

05 · Steering：AGENTS.md、CLAUDE.md、Memory 与 Skills

5.1 Steering 是提升概率，不是强制证明

仓库说明文件可以告诉 Agent：同类型参数使用对象参数、service 必须配套测试、文件如何命名等。这些规则应该稳定、项目特定、短小，而且最好能通过测试或钩子进一步强制。

5.2 Progressive Disclosure（渐进披露）

把所有规则塞进一个巨大的说明文件，会持续占用上下文，并让无关规则竞争注意力。更好的方式是：

AGENTS.md / CLAUDE.md
├── 只保留全局、高频、稳定规则
├── 链接到 React Router 指南
├── 链接到数据库指南
└── 链接到前端规范

Agent 默认只看到“地图”，需要时才读取对应材料。这就是课程贯穿始终的渐进披露思想。

5.3 Agent Skills

Skill 是一个可发现的文件夹，包含 SKILL.md、参考资料、脚本和其他资源。它把某种能力或工作流封装成可复用模块。

类型谁触发例子
Agent-invoked模型根据描述自动发现遇到 pnpm 缺失、SQLite 原生模块错误时自动修复
User-invoked用户显式调用写 PRD、生成 Issues、执行 TDD、迁移框架

好 Skill 倾向于简洁：触发条件清楚、主流程短、复杂参考材料单独存放。不要用大量文字重复模型本来就知道的常识。

5.4 Automatic Memory

自动记忆可以保存依赖安装方式、测试模式等经验，但必须定期审计。过时记忆会比没有记忆更危险，因为它会持续把 Agent 引向错误方向。

06 · 大任务：PRD 描述终点，计划描述路径

单个上下文放不下大型重构或完整产品功能时，不要硬塞，而要切分。

PRD.md：终点问题、目标用户、为什么做、用户故事、验收标准、范围外事项、关键决策。
PLAN.md / Issues：路径如何把终点拆成可单独完成、可验证、互不踩踏的小块。

6.1 好 PRD 的内容

  • 问题陈述与价值，而不只是功能清单；
  • 带编号的用户故事：谁、想做什么、为什么；
  • 权限、空状态、异常路径、筛选和 URL 状态等边界；
  • 将构建或修改的模块，以及在哪个边界测试；
  • 明确 out of scope，防止任务膨胀。

6.2 “Grill me” 的价值

让 Agent 连续追问设计选择，比让它立刻写一份看似完整的规格更有价值。真正的计划质量来自讨论中形成的共享理解，而不是模板长度。

6.3 不要过度规划

计划只记录跨阶段稳定的决定，例如路由、模块边界、是否新增依赖和关键数据来源。实现细节往往只有写代码时才会暴露，提前写成伪代码反而容易过时。

07 · Tracer Bullet：先打通纵向切片

LLM 天然容易“横向开发”：先写完全部数据库层，再写服务层，再写 UI。问题是直到很晚才能验证各层是否真正连通。

方式阶段划分反馈出现时间
横向分层数据库 → 服务 → 路由 → UI最后才看到端到端结果
纵向切片 / Tracer Bullet最小数据库 + 最小服务 + 最小 UI第一阶段就验证全栈链路

第一颗“曳光弹”不追求完整，而是用最小真实数据穿过所有关键层，尽早暴露未知问题。后续阶段沿已验证路径扩展。

计划提示语：“Use tracer bullets. Make phase one the smallest end-to-end vertical slice that can be manually verified.”

每阶段执行节奏：Explore → Implement → Review → Iterate → Commit → Clear。完成阶段就建立 Git 检查点，并为下一阶段释放全新上下文。

08 · 反馈循环：让正确性可观测

说明文件和 Skills 只能提高 Agent 做对的概率；类型、测试和运行结果才能给它确定性反馈。

8.1 反馈层级

  1. 格式化与 Lint：捕捉机械问题；
  2. 类型检查：捕捉接口和调用错误；
  3. 单元 / 集成测试：验证真实行为；
  4. 构建与运行：验证环境和整合；
  5. 人工 QA：验证体验、品味和业务目的。

8.2 Do Work Skill

课程把通用实现节奏封装成一个简洁 Skill：

1. Understand the task
2. Plan it if it is not already planned
3. Implement
4. Validate with the project's real feedback loops
5. Commit

关键是明确写出项目真实命令，如 pnpm run type-check 和 pnpm run test，而不是笼统说“确保质量”。

8.3 Pre-commit Hooks

人类嫌慢的 pre-commit 检查，对 Agent 反而很合适。使用 Husky / lint-staged，在提交前自动格式化、类型检查和测试；失败就阻止提交并把错误直接反馈给 Agent。

8.4 Red → Green → Refactor

  1. 写一个最小行为的失败测试，并确认它真的失败；
  2. 写最少代码让它通过；
  3. 保持测试为绿的前提下整理实现；
  4. 再加入下一条纵向行为。

失败测试能证明 Bug 或缺失行为真实存在，也迫使实现拥有可测试接口。课程尤其推荐把 Red-Green-Refactor 与 Tracer Bullet 结合。

09 · Ralph：把 Agent 放进循环

Ralph 不是神秘框架，本质就是反复用相同规则启动 Agent，让它每次选择并完成一个任务，直到没有工作。

while tasks_remain:
    context = recent_commits + open_issues + workflow_prompt
    run_agent(context)
    validate()
    commit()
    update_or_close_issue()

与手动多阶段计划相比，Ralph 移除了每阶段都要由人说“继续下一步”的机械环节。人可以只在开始时定义工作，在结束时做 QA。

9.1 从 HITL 逐步过渡到 AFK

  • 先运行一次并观察它如何探索、实现、申请权限、测试和提交；
  • 把常见错误修复为 Skill，把验证固化为钩子；
  • 任务描述稳定后，再允许多次自动迭代；
  • 设置最大迭代次数和明确结束信号，避免无限循环。

9.2 为什么 AFK 需要沙箱

AFK 模式不能不断等待用户批准命令，但直接跳过权限检查又会扩大风险。Docker 沙箱把 Agent 限制在容器内，使其无法访问主机下载目录、密钥和其他项目。

Git 保护代码历史；沙箱限制 Agent 能触碰的文件、进程和系统边界。二者互补。

10 · 从多阶段计划升级到 Kanban / GitHub Issues

大型计划太刚性：新增任务困难、并行性差、QA 反馈不易插入。课程后期更推荐把 PRD 转为带依赖关系的 Issues 图。

维度多阶段计划Kanban Issues
修改改计划会影响整体编号和顺序直接新增 Issue 和依赖
并行通常按 Phase 顺序所有无阻塞任务都可领取
QA需要另行安排QA 发现的问题自然进入队列
人机分工不明显Issue 可标记 HITL 或 AFK

10.1 PRD → Issues 工作流

  1. 定位 PRD，探索相关代码；
  2. 按纵向切片草拟 Issues；
  3. 标明依赖与 blocked-by 关系；
  4. 标记 HITL / AFK；
  5. 生成一个最终人工 QA Issue；
  6. 询问用户粒度和依赖是否合理，再创建任务。

10.2 Backlog 是人与 Agent 的异步接口

人一边检查已完成的功能并创建 Bug/Polish Issue，Ralph 一边从剩余队列挑选最高优先级任务。建议优先顺序通常是：关键 Bug → 开发基础设施 → 新功能 Tracer Bullet → Polish → 重构。

11 · 哪些工作必须有人参与

目标不是消灭人，而是让人只出现在判断价值最高的位置。

适合 HITL需求规划、产品取舍、架构接口、外部技术选型、原型审美、最终 QA。
适合 AFK明确 Bug、依赖升级、已有模式下的功能实现、测试补充、格式化、机械重构。

判断标准不是任务“难不难”，而是过程中是否需要品味、外部事实或不可自动观测的反馈。例如“按钮是否舒服”“这个架构是否符合团队价值”“产品是否真的解决问题”，仍需要人。

反模式：把一切都交给 AI 会得到缺少品味的产品；把一切都留在人手里，又浪费 Agent 擅长的耐心和吞吐量。

12 · Research 与 Prototype：提前消灭未知未知

12.1 Research 是缓存昂贵探索

如果后续 10 个 Agent 迭代都要重新搜索同一个 SDK，成本和错误率都会上升。可以先由人与 AI 一起比较方案、查官方资料、验证约束，保存一份临时 research.md。

研究文档应包含：候选方案、优缺点、选择理由、项目集成点、实现注意事项。它是下一步 PRD 和 Issues 的输入。

12.2 文档有生命周期

研究资产很容易腐化。完成实现和 QA 后，如果它不再持续提供价值，应删除或更新；Git 历史已经可以找回旧信息。陈旧文档会误导未来 Agent。

12.3 Prototype 把文字决定变成可体验对象

原型特别适合：

  • 前端设计：在开发者专用路由展示多个方案；
  • 新服务：验证鉴权、连接、权限和 SDK 行为；
  • 新架构：验证模块边界和端到端数据流。

课程案例先研究实时在线状态服务，再制作开发专用原型。原型虽用于验证，但仍运行类型检查和测试，并导出可复用组件，因此后续实现 Agent 能直接采用生产级资产。

Bug 修复和现有成熟模式的简单扩展通常不需要原型，因为目标行为已经清楚。

13 · 设计 AI 喜欢的代码库

13.1 AI 会放大软件熵

“AI 让代码变便宜”只说对了一半。Agent 很擅长快速添加代码，却不天然擅长删除、抽象和维护整体一致性，而且会模仿仓库里已有的坏模式。坏代码库会让每次探索更昂贵、测试反馈更弱、修改更危险。

13.2 Deep Modules（深模块）

深模块用很薄、稳定的接口隐藏大量内部实现：

const quiz = createQuizModule({ db, scoringStrategy, quizPassXp })

quiz.getQuizForLesson(lessonId)
quiz.getBestAttempt(userId, quizId)
quiz.submitAttempt({ userId, quizId, answers })
quiz.saveQuiz(input)
quiz.deleteQuiz(quizId)

相比几十个浅层小文件和互相穿透的调用，深模块让 Agent 只读接口就知道能力边界；集成测试也能从外部验证大块行为，而不与内部实现绑定。

13.3 人类成为接口与架构设计者

理想分工是：人设计模块边界、接口和价值取舍；AI 填充实现。审查重点从逐行检查内部代码，转向接口、测试和端到端行为。

13.4 把模块意识前置到 PRD

  • 列出要新增或修改的主要模块；
  • 寻找可封装为深模块的机会；
  • 与人确认模块是否符合预期；
  • 确认哪些边界必须有测试。

14 · 一套可直接采用的实战 Playbook

A. 小 Bug / 小功能

  1. 新建 Git 分支或 worktree，清空 Agent 上下文；
  2. 描述预期行为与实际行为；
  3. 要求先写失败测试重现问题；
  4. 最小修复，运行类型、相关测试、全量测试；
  5. 人工验证，提交并记录结果。

B. 单上下文中型功能

  1. 进入 Plan Mode，要求探索并追问设计决定；
  2. 确认权限、异常、空状态和验收标准；
  3. 检查上下文预算，决定保留讨论还是 Clear 后执行；
  4. 用 Tracer Bullet + Red-Green-Refactor 实现；
  5. 自动验证 + 人工 QA。

C. 大型功能

  1. 有外部未知时先 Research，有体验未知时先 Prototype；
  2. 人与 Agent 一起写 PRD，强调 Why、模块和测试边界；
  3. 把 PRD 转成带依赖的纵向 Issues，区分 HITL / AFK；
  4. 在沙箱中运行 Ralph，限制迭代次数；
  5. 人执行最终 QA Issue，把发现继续加入 Backlog。

D. 团队长期治理

  • 说明文件只放稳定、高频约定；
  • 低频知识封装为 Skills 并渐进披露；
  • 自动 Memory、研究文档和 Skills 定期审计；
  • pre-commit / CI 强制运行可靠反馈；
  • 持续把浅模块深化为清晰接口；
  • 权限最小化，AFK Agent 运行在沙箱中。

15 · 关键概念速查

概念一句话解释
Smart Zone模型注意力最可靠的上下文前段，应尽量把真正实现留在这里。
Plan Mode只读探索与需求澄清阶段，避免过早写代码。
Progressive Disclosure默认只提供地图，需要时再读取详细规则和资料。
Agent Skill封装可发现的工作流、知识、脚本和资源。
PRD描述要到达的产品终点、原因和验收标准。
Tracer Bullet先做一条最小但真实的端到端纵向切片。
Red-Green-Refactor失败测试 → 最小实现 → 整理代码的反馈循环。
Ralph把 Agent 放入重复任务循环，直到队列为空。
HITL / AFK需要人类判断的任务 / 可以自主完成的任务。

最终自检：什么时候可以放心让 Agent AFK？
  • 任务可以从 Issue 中独立理解，且没有未决产品选择；
  • 仓库已有可运行的类型、测试、格式化和构建反馈；
  • Agent 知道何时提交、何时关闭任务、何时停止；
  • 权限经过最小化，运行环境与主机隔离；
  • 有最大迭代次数，失败结果可恢复；
  • 结束后仍安排人工 QA，而不是把测试通过等同于产品正确。

最重要的转变：不要只问“模型能不能写这段代码”，而要问“我是否建立了一个让它能持续做对的环境”。
