01 · 先给结论：面试时你应该怎么定义它

这不是让 AI 从零做产品的“提示词合集”，而是后端工程师把 PD 的 PRD 转换成可实现、可验证交付物的一套轻量编排体系。

它解决的核心问题不是让 AI 多写代码，而是降低 AI 研发中的需求偏差、上下文退化、验证不足、架构熵增和无人值守风险。

你在面试中可以用下面四句话定调：

  1. 我把 AI 当作能执行工具的非确定性工程代理，不是代码补全器。
  2. 收到 PRD 后，我通过 Skill 完成需求与代码对齐、信息缺口分流、工程规格化、纵向切片、实现和审查。
  3. 每个阶段都有输入、完成标准和持久化产物，关键正确性尽量由测试和工具反馈，而不是靠 Prompt 信任。
  4. 人负责目标、领域语言、架构和产品判断；Agent 负责探索、实现、重复验证和可委派工作。
最重要的面试转换：不要说“PD 给我 PRD，我就让 AI 生成代码”。要说“我借鉴并改造了这套 Skill，把 PRD 审核、业务决策回收、工程 Spec、任务分解、TDD 和 Review 固化为可重复的后端研发工作流”。

02 · 项目完整画像：它到底是什么

仓库定位是 Skills for Real Engineers。作者明确反对由一个大框架接管全部流程，更倾向于小型、可组合、可修改、模型无关的 Skill。官方 README 将主要失败模式归纳为：需求不一致、语言不一致、代码不可验证，以及 AI 加速软件熵。

2.2 两种调用模型

User-invoked 用户显式调用负责高层编排和带有人类意图的流程，如 grill-with-docs、to-spec、implement。它不占模型的自动发现上下文，但人要记得调用。
Model-invoked 模型可自动发现负责可复用纪律和参考知识，如 tdd、code-review、research、codebase-design。描述是常驻的 context pointer。

用户 Skill 可以显式调用模型 Skill，但不能调用另一个用户 Skill。这样做既保持人对高层流程的控制，又让 Agent 在实现过程中自动调用通用纪律。

2.3 Router Skill

ask-matt 是路由器。随着用户 Skill 增多，人类的认知负担会上升，因此只记住一个入口，由它说明该走哪条流程。它不能替人调用其他 user-invoked Skill，只能给出路线。

04 · 我的真实场景：PD 给 PRD 后，后端怎么跑

工作入口不是“我有一个想法”，而是“PD 已经提交 PRD”。因此不需要让 AI 从零发明需求，而是让它把 PRD、现有代码和技术约束对齐，再把业务文档转成可实现、可测试、可验收的工程规格。

PD 的 PRD→grill-with-docs→补齐未决问题→to-spec→to-tickets→逐个 implement→TDD + Review→PR
这仍然不是机械流水线。
小改动可以跳过 to-spec 和 to-tickets；复杂业务功能才走完整链路。to-questionnaire、research、prototype 和 ADR 都是遇到对应阻塞时插入的分支，不是固定关卡。

0 项目级准备：通常只做一次

setup-matt-pocock-skills 用来探索仓库并配置 Issue tracker、triage label、CONTEXT 和 ADR 布局。它属于项目初始化，不是每收到一份 PRD 都重新运行。

1 收到 PRD：先做 grill-with-docs

把 PRD 作为输入，显式调用 grill-with-docs。它一边阅读 PRD，一边探索现有代码、数据模型、接口和测试，把三件事对齐：业务想要什么、系统现在是什么样、两者之间还缺哪些决定。

例如 PRD 只写“用户可以取消订单”，Agent 应继续暴露：哪些状态允许取消、退款和库存如何联动、重复取消怎么处理、退款失败怎么办、老客户端是否兼容。此时产物是“已确认事项 + 待确认事项”，还不是直接生成代码。

2 未决问题分流：答案到底在哪里

  • 代码能回答：例如订单表结构、现有幂等机制、错误码规范——让 Agent 继续查仓库，不要拿工程事实打扰 PD。
  • PD 或业务 owner 才能决定：例如哪些状态允许取消、优惠券是否退回、客服能否强制操作——问题少就直接沟通，问题多且适合异步确认时，显式调用 to-questionnaire。
  • 官方资料能回答：例如支付回调是否重试、SDK 限流规则——调用 research 查官方文档、源码和协议。
  • 必须实验才知道：例如 SDK 与当前框架是否兼容、消息顺序是否满足要求——调用 prototype 做只回答一个问题的最小技术探针。
to-questionnaire 的准确位置：
grill-with-docs 进行到一半，发现关键答案只在别人脑中，这时暂停并生成一份给单个接收人的 Markdown 问卷。它不会替你发送消息。答案回来后，把回答带回原会话，继续 grilling，或者进入 to-spec。

3 需求补齐后：用 to-spec 转成工程规格

to-spec 不重复访谈，而是综合 PRD、讨论结论和代码探索结果。PRD 主要回答“业务为什么做、用户要什么”；工程 Spec 进一步固定状态转换、接口行为、幂等语义、事务与一致性、兼容策略、异常处理、监控告警、测试决定和范围外事项。

如果只是边界非常明确的小接口改动，可以不写完整 Spec，直接进入 implement；如果涉及跨模块、跨团队或复杂状态机，应该保留 Spec 作为共同验收契约。

4 出现重大技术取舍时：补充 ADR

ADR 不是每个需求都写。只有决定难以逆转、存在真实取舍、以后脱离上下文会让人困惑时才记录。例如“订单取消采用本地事务 + Outbox，而不是分布式事务”。普通字段或接口修改不需要 ADR。

5 复杂需求：用 to-tickets 转成任务图

to-tickets 不应机械拆成“建表、DAO、Service、Controller”，而应拆成可独立验证的端到端 tracer bullet，例如“待支付订单取消”“已支付订单取消并退款”“退款失败补偿”。每个 Issue 声明真实的 blocking edges，并尽量能在一个全新上下文内完成。

对无法纵向切分的 wide refactor，采用 expand → migrate batches → contract，保持每批 CI 可绿。

6 实现

从当前没有阻塞的 Issue 中选择一个，在相对干净的新上下文中运行 implement。它重新读取 Issue、Spec 和相关代码，在预先确认的 seam 上调用 tdd，经常运行单测和类型检查，最后运行全量测试。

7 双轴审查

code-review 固定 merge-base 后并行启动两个审查 Agent：

  • Standards：仓库规范 + Fowler code smell baseline；
  • Spec：遗漏、部分实现、范围膨胀和行为错误。

两个报告不合并排序。因为“写得规范但需求错了”和“需求实现了但破坏规范”是不同风险。问题修复、测试通过后，再提交 PR 进入团队正常评审流程。

4.1 按需求大小选择最短闭环

任务类型建议路线使用说明
小 Bugdiagnosing-bugs → tdd → code-review先建立精确复现和根因证据，再用回归测试锁住修复；不需要补完整 Spec。
明确的小接口grill-with-docs → implement → tdd → code-review快速核对 PRD 与现有接口约束，边界清楚就直接进入短实现闭环。
复杂业务功能grill-with-docs → to-spec → to-tickets → implement → tdd → code-review先形成共同工程契约，再拆成带依赖、可独立验证的端到端 Issues。
外部系统接入research / prototype → to-spec 或 implement官方资料能回答就 research；必须运行才能知道就 prototype。复杂接入形成 Spec，简单接入可直接实现。
业务规则需要别人确认在 grilling 中途插入 to-questionnaire答案在 PD、业务专家或上下游 owner 脑中时使用；回答回来后继续 grilling 或进入 to-spec。

路由原则：不是看哪个 Skill 功能最强，而是看当前任务被什么阻塞。能走短闭环就不机械执行全套流程；只有复杂度和风险值得时，才增加 Spec、Issues、原型或异步问卷。

面试口语版：
“PD 给我 PRD 后，我不会直接让 AI 写代码。我先让它结合 PRD 和现有代码做 grilling。代码能回答的问题让 AI 自己查，业务规则不清楚的再找 PD，问题多时用 to-questionnaire 生成结构化问卷。需求补齐后，用 to-spec 转成工程规格，复杂需求再用 to-tickets 拆成端到端 Issue，最后逐个 implement，并通过 TDD 和双轴 code review 建立反馈闭环。”

05 · 真正值得面试讲的底层原则

5.1 Context pointer 与渐进披露

Skill description、AGENTS.md 中的一行链接，本质都是 context pointer：它描述外部材料是什么，以及什么条件下应该读取。指针措辞决定调用可靠性。

Context load始终在模型上下文里的成本，例如 model-invoked Skill 的 description、全局 AGENTS 指令。
Cognitive load人要记得哪些 Skill 存在、什么时候调用的成本。user-invoked Skill 把成本放在人身上。

因此不是所有内容都放 AGENTS.md，也不是所有内容都拆 Skill。应把所有分支都需要的步骤内联，把仅某些分支需要的参考材料放到指针之后。

5.2 单一事实源与防沉积

环境本身也是事实源。package scripts、目录结构、CLI help 可以直接查，就不应重复写进文档。只缓存“环境无法表达的东西”：团队约定、选择理由、特殊陷阱。否则文档会形成过时 sediment。

5.3 Leading words

使用模型预训练中已有的高密度词汇来锚定行为，例如 tracer bullet、frontier、fog of war、tight loop、deep module。它们比重复一长串解释更稳定、更省上下文。

5.4 Completion criteria

每个步骤应有可检查且足够严格的完成条件。比如调试第一阶段不是“理解问题”，而是“已经运行过一个能对用户精确症状变红、快速、稳定、可无人运行的命令”。

5.5 Seam 是测试与架构的连接点

Seam 是可替换行为的位置，测试从公共接口穿过 seam 观察行为。测试前先和人确认哪些 seam 值得测试，优先选择最高层、最少数量的 seam。接口设计不好时，先调用 codebase-design，而不是写一堆内部耦合测试。

5.6 人机边界

事实检索是 Agent 的工作；目标选择、产品品味、领域定义、架构权衡是人的工作。Skill 的价值就是把这条边界变成明确流程。

08 · 面试介绍稿：30 秒、1 分钟、3 分钟

8.1 30 秒电梯版本

我不是把 AI 当代码补全，而是用一套可组合的 Agent Skills 管理后端研发流程。PD 给出 PRD 后，我先让 Agent 结合现有代码做结构化需求对齐：工程事实由 AI 自己查，业务规则回到 PD 确认；再形成工程 Spec，并拆成带依赖的端到端 Issues。每个 Issue 在独立上下文里用 TDD 实现，最后按代码规范和需求符合度做双轴 Review。这样既提升了交付效率，也把需求偏差、上下文退化、验证不足和架构熵增控制在可观测范围内。

8.2 1 分钟标准版本

我使用 Matt Pocock 这套 Skills，但会按后端研发场景裁剪。入口通常是 PD 的 PRD：我先用 grill-with-docs 让 Agent 同时阅读 PRD 和代码，把需求展开成设计树。表结构、现有接口和幂等机制等工程事实由 Agent 自己查；取消条件、退款口径等业务决定交给 PD，问题多时用 to-questionnaire 生成异步问卷。信息补齐后，用 to-spec 形成工程规格，复杂需求再按 tracer bullet 拆成带 blocking edges 的 Issues。每个 Issue 在新上下文里围绕稳定 seam 做 Red-Green TDD，最后分别检查代码规范和 Spec 符合度。我的目标不是让 AI 一次写对，而是让需求来源明确、错误尽早暴露、交付过程可以恢复。

8.3 3 分钟深度版本

我是以后端工程师的工作方式来使用这套 Skills。入口一般是 PD 已经提供 PRD。第一步用 grill-with-docs 同时阅读 PRD 和代码库，逐轮展开当前决策 frontier。它不是重新做一遍产品设计，而是检查 PRD 放进现有系统以后还有哪些状态、权限、异常和兼容问题。工程事实由 Agent 查代码；业务问题交给 PD 或真正的 owner，问题较多时用 to-questionnaire 异步回收。项目用 CONTEXT.md 维护领域 glossary，只有难以逆转且存在真实权衡的决定才写 ADR。

第三层是规划。讨论形成 Spec 后，不按数据库、后端、前端横向拆任务，而按 tracer bullet 拆成端到端 Issue，并显式标注 blocking edges。这样任何没有 blocker 的 Issue 都是当前 frontier，可以并行领取，而且每个 Issue 能在一个新上下文里完成，避免上下文越积越差。

第四层是实现与验证。测试前先确认公共 seam，在这个 seam 上一个失败测试配一个最小实现，逐个 Red-Green，而不是一次性写完所有测试和代码。难 Bug 则先花主要精力构造能对精确症状变红的 tight loop，之后才做最小复现、3 到 5 个可证伪假设和定向 instrumentation。

第五层是 Review 和架构治理。Review 拆成 Standards 与 Spec 两个独立维度，避免规范性掩盖需求错误。架构上采用 deep module 的思路，用小接口隐藏复杂实现，把测试放在稳定 seam 上，追求 caller leverage 和维护 locality。

第六层是运行治理。Issue 通过 triage 状态机区分 needs-info、ready-for-agent、ready-for-human 等状态；需要人工点击、密钥或外部控制台的工作，生成交互式 wizard，而不是让 Agent 猜。整体上，我让 AI 承担吞吐量，让人掌握关键判断，并用代码、测试、Issue 和文档作为跨会话的持久化事实源。

8.4 如果面试官问“这不就是套 Prompt 吗？”

单个 Skill 的载体确实是 Markdown 指令，但体系不是靠一段 Prompt 工作。它有调用权限、路由、信息层级、Issue 状态机、blocking graph、TDD 反馈、Git diff Review 和持久化领域文档。Prompt 只负责调度行为；正确性仍由测试、类型、代码和人工 QA 提供。对我来说它更接近轻量的 Agent workflow DSL，而不是聊天话术。

09 · 项目案例怎么讲：可直接套用的 STAR 模板

下面以“PD 提出订单取消需求”为后端案例。请把业务名称、技术栈、数据和结果替换为你的真实项目，绝对不要虚构指标。

9.1 Situation

PD 提供了一份“支持用户取消订单”的 PRD，但没有完全说明不同订单状态、退款失败、库存回补、优惠券退回、重复请求和上下游回调的处理口径。现有订单系统又已经存在多种状态和异步消息。

9.2 Task

我的任务是把业务 PRD 转成可以落地和验收的后端方案，在不替 PD 猜业务规则的前提下，确保状态流转、幂等、一致性和异常补偿都有明确设计。

9.3 Action

  1. 把 PRD 交给 grill-with-docs，让它结合订单状态机、退款接口、消息和现有测试找出需求缺口。
  2. Agent 自己查表结构、幂等组件和错误码；把“哪些状态可取消、优惠券是否退回”等业务决定整理给 PD，问题多时用 to-questionnaire。
  3. 支付平台行为用 research 查官方资料；SDK 兼容性或消息行为不确定时，用 prototype 做最小技术探针。
  4. 回答补齐后形成工程 Spec，明确状态转换、接口语义、事务一致性、补偿、监控、测试 seam 和 out of scope。
  5. 按“待支付取消、已支付取消并退款、退款失败补偿”等 tracer bullet 拆 Issues，并建立真实 blocking edges。
  6. 每个 Issue 启动新上下文，在确认 seam 上做 Red-Green TDD，持续跑单测和类型检查。
  7. 结束时运行全量测试，并用 Standards / Spec 两个 Reviewer 检查。
  8. 人工和 PD 按验收场景做 QA，将新发现转成 Issue，而不是在高负荷旧上下文里继续补丁。

9.4 Result

只写真实证据，例如：

  • 将一个大需求拆成 X 个可独立验证 Issue，其中 Y 个可并行；
  • 新增 X 条集成测试，关键业务路径覆盖到某个公共 seam；
  • Review 发现 X 个需求遗漏和 X 个规范问题；
  • 从提交记录看交付时间由 X 天降到 Y 天；
  • 上线后某类缺陷或回滚次数下降；
  • 如果没有量化数据，就说“实现了什么可复现流程”，不要编百分比。

9.5 口语化示范

有一次 PD 给了订单取消的 PRD。我没有直接让 AI 写接口，而是先让它结合 PRD 和现有订单代码做 grilling。它查出了当前状态机、退款链路和幂等机制，同时暴露出几项 PRD 没写清楚的业务规则。我把这些问题交给 PD 确认，而不是让 AI 猜。答案回来后，我整理成工程 Spec，再按待支付取消、已支付退款和失败补偿拆成几个端到端 Issues。实现时每个 Issue 用新上下文，在订单模块公共接口上先写失败测试，再做最小实现，最后分别检查代码规范和 Spec 覆盖。这个过程最有价值的地方，是把业务决定、工程事实和技术验证分开处理，每种错误都能更早暴露。
请准备三个真实案例：一个新功能、一个难 Bug、一个架构改进。这样面试官无论从交付、调试还是设计追问，你都有事实可讲。

10 · 高频追问与示范回答

Q1：PD 已经给了 PRD，为什么还要 grilling？
PRD 说明业务目标，但通常不会完整描述它进入现有系统后的所有工程边界。我用 grill-with-docs 同时看 PRD 和代码，检查状态流转、幂等、异常补偿、兼容性和监控。代码事实让 Agent 自己查，业务决定再请 PD 确认，所以 grilling 是需求落地审查，不是推翻 PRD 或重新做产品设计。
Q2：为什么不用一份超详细 PRD 直接让 AI 做完？
PRD 和工程 Spec 的职责不同。PRD 主要描述业务目标和用户行为；后端还要结合现状确定接口语义、数据变化、一致性、异常和验收方式。大任务一次做完还会产生上下文压力和反馈延迟，所以我先固化工程 Spec，再拆成可单会话完成的 tracer-bullet Issues。
Q3：后端任务为什么也强调纵向切片？
这里的纵向不是一定穿过前端，而是穿过完成一项后端行为所需的真实层次，例如数据、领域逻辑、接口、消息和测试。“支持待支付订单取消”可以独立验证；“只建表”或“只写 DAO”不能证明业务路径成立。后续切片再在已验证路径上扩展。
Q4：TDD 会不会拖慢 AI？
AI 的优势正是耐心执行重复验证。TDD 的成本主要是循环次数，但它提供了可执行反馈，减少后期大范围调试。关键不是机械追求覆盖率，而是在预先确认的公共 seam 上逐个行为 Red-Green，避免对内部实现写脆弱测试。
Q5：你说的 seam 是什么？
Seam 是可以替换行为而无需在调用点修改代码的位置，也是模块公共接口所在的位置。测试从 seam 调用接口并观察外部行为。一个好的 seam 能隐藏复杂实现，让测试在重构后仍然稳定。
Q6：AI 调试时最容易犯什么错误？
最常见是先看代码就建立单一假设，然后一路验证自己。我的调试流程先构造一个针对精确用户症状的 tight loop，并最小化复现；之后列 3 到 5 个可证伪假设，每次只改一个变量并做定向 instrumentation。修复前把最小复现变成 regression test，再回跑原始场景。
Q7：如何防止 AI 产生大量低质量代码？
第一是任务小而完整；第二是类型、测试、Lint 和运行结果形成反馈；第三是双轴 Review；第四是持续改进代码库结构。AI 会模仿现有代码，所以代码库本身是最强 Prompt。长期要通过 deep module 提高 locality，减少一次变更散落多个文件。
Q8：Deep module 和普通 service 有什么不同？
Module 是任何有 interface 和 implementation 的结构，不限定技术形态。深不深看的是接口提供的 leverage，而不是文件大小。一个 deep module 用很小的接口隐藏大量业务复杂度，调用者和测试只需要理解这个接口；一个浅 service 可能只是透传，删除它并不会消除复杂度，只会少一层跳转。
Q9：为什么 Review 要分 Standards 和 Spec？
因为它们是正交风险。代码可能完全符合规范却实现错需求，也可能功能正确但破坏项目设计。两个 Reviewer 并行还能避免一个维度的上下文影响另一个。最后保留两个报告，不强行合并成一个优先级列表。
Q10：什么可以交给 AI，什么必须由人做？
表结构、调用链和现有规范等工程事实由 Agent 查；官方协议由 research 查；代码实现和重复测试也适合交给 Agent。业务口径由 PD 或业务 owner 决定，关键架构取舍和最终验收由工程师负责。答案在别人脑中且问题较多时，我用 to-questionnaire 收集，而不是让 AI 代替对方决策。
Q11：多个 Agent 会话怎么共享上下文？
不靠复制整段聊天，而靠 context pointers 指向持久化事实：Spec、Issue、CONTEXT、ADR、research、prototype branch、commit 和 diff。每个 Issue 是自包含输入，所以实现会话结束后上下文可以丢弃。只有跨目录、跨 harness 或交给同事时才生成 handoff。
Q12：什么时候 clear、compact、handoff 或 subagent？
同阶段且原始信息仍有价值时继续；下一阶段不需要旧上下文时 clear；需要可移交到新目录、新工具或同事时 handoff；独立且边界清楚的读任务用 subagent；compact 是需要保留大量当前上下文但窗口压力较高时的兜底，不是默认第一选择。
Q13：如何控制 Agent 的安全风险？
最小权限、敏感信息只通过环境变量、展示输出先脱敏、危险 Git 命令用 hook 阻止、不可逆步骤设置确认门，无人值守执行放进沙箱并设置迭代上限。Git 只负责代码历史，不能替代文件系统、进程和凭证隔离。
Q14：这套流程有什么缺点？
它增加了前置思考和文档治理成本，小改动全套跑一遍会过度工程；Skill description 和文档也可能过时，形成 context sediment；Agent 自动调用存在概率性，TDD 也可能写出低价值测试。因此我按任务规模裁剪流程，并定期审计 Skills、CONTEXT、ADR 和指针。
Q15：你有没有改造这套 Skill？
面试前请换成真实内容。推荐从三个方向讲：把真实项目的 typecheck/test/browser 命令写入实现 Skill；加入团队编码规范和 Issue tracker 标签；根据项目领域增加 CONTEXT 词汇、测试 seam 和 Review 规则。重点讲为什么改、改变了什么行为，以及怎样验证有效。
Q16：如何评价 AI Coding 的 ROI？
我不会只统计生成代码量，而会看 lead time、一次通过率、返工次数、Review 发现的问题类型、测试新增、任务并行度、Agent 等待人工时间和上线缺陷。还要计入研究、Prompt 治理和 QA 成本。只有整体交付周期和质量改善，才是真实 ROI。
Q17：什么时候使用 to-questionnaire？
当 grilling 暴露的问题不在我或代码库中，而在某一个 PD、业务专家、架构师或上下游负责人脑中时使用。它生成一份给单个接收人的异步 Markdown 问卷，不会自动发送。问题少时直接沟通更高效；多个接收人则分别生成，答案回来后继续 grilling 或进入 to-spec。

11 · 面试时容易讲错的地方

不要这样说改成这样说
“装了 Skill，AI 就能自己开发。”Skill 提高流程一致性，正确性仍由反馈循环、权限边界和 QA 保证。
“AI 写代码比人快很多。”AI 提升实现吞吐，但可能加速熵增，因此我把重点放在切片、测试和架构治理。
“TDD 能保证没有 Bug。”TDD 给关键 seam 提供可执行回归信号，不能覆盖产品体验和未建模风险。
“我会 37 个 Skill。”我把它们归纳为六层系统，并按任务规模选择最小必要流程。
“Prompt 写得越详细越好。”过长上下文会稀释注意力；稳定信息落到正确事实源，按需渐进披露。
“有 Git 就安全。”Git 保护历史；hook、最小权限和沙箱控制影响范围。
“这些指标提升了 50%。”只给可证明的数据，并说明测量口径；没有数据就给提交、测试和 Issue 证据。

11.1 不要把别人的方法包装成自己的发明

诚实说你基于开源 Skill 学习和改造，明确指出借鉴了 Tracer Bullet、TDD、DDD ubiquitous language、Fowler smells 和 Ousterhout deep module。你的价值在于理解、落地、验证和适配。

11.2 不要只讲工具，不讲业务结果

面试官真正关心的是：需求有没有更准、交付有没有更快、质量有没有变好、团队能否复用、出问题能否恢复。Skill 名称只是支撑材料。

我的 AI Coding 五句话

  1. AI 是非确定性执行者，软件工程反馈比 Prompt 崇拜重要。
  2. PD 给 PRD 后先结合代码做 grilling；工程事实让 Agent 查，业务决定回到真正的 owner。
  3. 大任务变成 tracer-bullet Issue 图，每张 Issue 一个新上下文。
  4. 在公共 seam 上 Red-Green，结束后 Standards / Spec 双轴 Review。
  5. 长期通过 deep modules、指针治理和安全边界控制软件熵。
